# Ownership, domains and publication

- Resolve a reference website separately from the user's destination. Inspect its appearance and assets as permitted, but do not assume the user owns it or can replace its deployment. Confirm destination ownership through the connected provider's project/account records.
- Inspect current source, branch and changes before editing. Check all relevant branches when asked whether someone pushed. A deployed preview may come from a local upload; deployment and Git history can differ. State exactly which was checked.
- Discover existing connections and try a narrow read before requesting setup. An available plugin is not proof of repository access; an empty result or one 404 is not proof that an account is disconnected. Recheck the named account/repository when the user says it is connected. Do not initiate an unrelated account connection to solve a transient access error.
- For an existing project, reuse its exact provider ID. For a new copy, establish that the user requested a separate project, choose the verified account/team, create it once and record its ID before deploying. Never send an unspecified deployment target or silently update someone else's site.
- Changing a site label may leave the hosting provider and account names in the URL. A different provider can remove the unwanted previous provider/account identifiers, but its default address still has that provider's suffix (for example, `venue-name.netlify.app`). A provider-free address requires a custom domain the user controls. Do not claim a domain is attached until DNS/validation completes. Never purchase a domain or upgrade a plan without spending authority.
- Use the provider's supported deployment path. Scope uploads to the site files and required configuration, excluding credentials, client working files and unrelated repositories. Keep temporary tokens in memory and pass them through protected input; do not include them in public source, logs or handoffs.
- Wait for a terminal successful deployment, then check the actual final URL as an unauthenticated visitor when the desired audience is public. New projects can default to team-only protection. Respect existing access instructions; if removing protection requires explicit approval, ask for that exact change and resume once authorized. Never describe a sign-in-protected link as public.
- Verify the embedded media URL, playback and direct link. Compare the hosted file hash with the approved upload when serving it unchanged. Check seeking/range support on the real host; identify codec or browser limitations separately from deployment status. Record any checks not performed.
- If a publish call is interrupted, inspect its deployment/version status before retrying. Do not assume cancellation prevented publication. Report any completed side effect accurately.

Record the final hosting project ID, account/team, URL, audience, saved version/deploy ID, source commit or upload hash, approved media hash, completed checks and remaining limitations in the project checkpoint. Keep client-specific values outside this reusable repository.
